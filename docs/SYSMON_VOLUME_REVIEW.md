# 研究覆盖与日志体积复核

日期：2026-09-12。结论：**标准 Sysmon 命令可直接加载本 XML；安装可以简化。核心采集范围符合当前研究，但不能在没有新规则试采数据时保证每轮日志很小。**

本次仅整理安装包、说明和可选检查工具。`sysmonconfig-export.xml` 与此前研究版 XML 逐字节相同，保留原规则版本和 SHA256；没有建立新的采集规则批次。若从 SwiftOnSecurity 切换到这份研究规则，则仍属于规则变更，应保存新快照和配置指纹。

## 1. 按研究目标核对

| 需要的内容 | 配置与实际能力 | 覆盖边界 |
|---|---|---|
| SHA256.exe 是否启动、何时退出 | 1/5 无路径筛选；SHA256、ProcessGuid、ParentProcessGuid 支持来源关联 | 主进程出现不证明已成功加密；退出事件也可能在窗口结束之后 |
| 子进程与执行上下文 | 1 保留命令行、父子进程字段；5 保留结束 | 注入目标不是普通子进程；进程树并不涵盖全部间接影响 |
| 文档创建、覆盖、删除 | 11/26 不限路径或扩展名 | 不是逐次文件写入、读取或通用重命名审计；没有每次加密函数调用 |
| 批量文件行为的时间顺序 | 时间字段和文件事件留在原 XML，后续可建立系统窗口及进程关联视图 | Sysmon 检测时间、事件写入时间与主机收到时间不同；保留原字段并明确时序定义 |
| 修改注册表 | 12–14 无配置级过滤 | 包含大量正常行为；仅有事件不能定性恶意 |
| 域名访问线索，不采网络报文 | 22 保留 DNS 查询，3 保留 Sysmon 可见的连接 | 离线时可能只有失败 DNS，也可能两者都没有；不能据此推断没有尝试联网；不能恢复完整 HTTP URL/请求正文 |
| 跨进程活动、持久化上下文 | 8/9/15/17–22/25/29 放开；6/7/10 保留上游条件 | 7/10 有人工规则造成的盲点；WMI 19–21 不是所有 WMI 操作 |
| 采集异常 | 4/16/255 等质量线索与接收端 metadata 保留 | 被清除前未送出的事件、采集服务退出或源头未产生日志，无法靠 XML 配置补回 |
| 家族标签 | 仍由样本清单、metadata 和人工审查提供 | Sysmon 配置不会自动输出勒索软件家族 |

因此，本配置适合提供行为分类的输入，而非直接给出逐事件真值。正常运行和勒索运行应使用同一份配置、共同的文档语料与环境设置。

事件与命令语义参考：[微软 Sysmon 文档](https://learn.microsoft.com/en-us/sysinternals/downloads/sysmon)。已有研究与更详细的设计理由参见原研究配置包的 README；本次未增加新的文献结论。

## 2. 最容易使日志增大的位置

| 类别 | 体积风险 | 当前取舍 |
|---|---|---|
| 11/26 文件创建与删除 | 文件数量大、批量解压/同步/加密时可能很高 | 保留。这是比较正常批量操作与勒索活动的重要信号，不能按固定条数截断 |
| 12–14 注册表 | 安装程序、浏览器、后台系统服务可能产生大量变化 | 当前保持全量；试采若占主要负载，再按实际事件分布统一调整并发布新规则版本 |
| 7/10 模块加载、进程访问 | 全开可能很高，筛选后也未必很低 | 已保留 default+ 选择性规则，没有全量开启 |
| 17/18 管道、22 DNS | 取决于软件及后台活动 | 保留，检查实际贡献；断网不意味着没有 DNS 事件 |
| 15/29 文件流、可执行文件检测 | 安装与解压 PE 文件时可能增加事件及计算负担 | 保留上下文；是否值得保留可在试采和消融后判断 |
| 23/24 文件归档、剪贴板 | 除事件外还可能保存内容 | 关闭，避免本研究不使用的归档负担 |

仅计算 SHA256，关闭反向 DNS 补全及吊销查询，是现有减少额外工作的措施。27/28 的阻止功能关闭；关闭阻止功能不等于采集完全没有 CPU、内存或时间开销。

**300 秒只约束实验观察时长，不限制事件数或文件大小。** 现有接收器也保存启动前基线和排空尾部，最终 XML 可以超过严格 300 秒窗口的事件范围。

粗略的存储规划示例，假设平均每条保存记录为 2 KiB（是假设，不是新规则实测值）：

| 每轮事件数 | 约 XML 大小 |
|---|---:|
| 10,000 | 19.5 MiB |
| 100,000 | 195.3 MiB |

500 轮若平均 20 MiB，XML 合计约 9.8 GiB，尚不含备份及派生数据。可以在采集完成且校验后增加无损压缩副本用于存储；压缩不解决采集中队列积压，原始 XML 哈希与压缩文件哈希也要区分。本包没有改动接收器输出格式。

## 3. 当前工作流更应关注传输峰值

本地项目 `guest/Collector.cs` 的默认有界队列为 **8192 个事件 / 64 MiB 的估算 XML 字符串负载**，先触发哪个限制就可能丢弃。此处 64 MiB 不是所有对象的总内存上限。默认串口参数为 115200、8N1；VMware 虚拟串口实际吞吐需要实测，不能仅由该数字保证容量。

因此，磁盘还能装下 20 MiB，并不保证它能在既定窗口及 120 秒排空时间内顺利传完；反过来，一个正常完成且没有丢弃的大 XML 也不应只因大小被判为坏样本。

先进行短基线、一次文本编辑和一次正常批量文件操作的试采，再用已有隔离实验流程检查少量勒索运行。观察 observed/sent/received、dropped、watcher_errors、序号、最终 END、队列峰值以及排空是否超时。全量正常安装程序也应测试，因为正常样本可能比勒索样本更吵。

如果出现积压，应先查哪类事件、哪些共同后台任务贡献最多。共同环境设置和任何规则调整必须对正常与恶意数据一致，并固定到新快照/版本。不要仅扩大队列或无限延长等待，也不要按标签分别过滤；不能通过“每轮只保存前 N 条”来控制大小，否则时序窗口失真。

## 4. 本次实际读到的旧数据

只读检查 `D:\SysmonLogs` 和 `D:\SysmonBenignLogs`：

- 共 49 个含 metadata 的目录，包含历史测试与异常运行，不等于 49 个有效研究样本。
- XML 合计约 6.2488 MiB；中位数约 0.1310 MiB；最大约 0.2476 MiB。
- 43 轮具有 final stats，6 轮只有最后心跳统计。工具列出 12 轮存在需复核事项，这不是重新标定的“失败数”或标签。
- metadata 均未提供 `sysmon_config_sha256` 字段；这些记录不能作为新规则已加载且吞吐合格的证据。根据此前工作记录，它们属于旧采集阶段。

这次读取只计算文件大小和检查 metadata，不重做 XML 内容、哈希及行为真实性审核。旧数据较小不能证明本配置试采后同样小。
