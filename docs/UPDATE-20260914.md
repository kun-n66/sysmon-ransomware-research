# 2026-09-14：VMware Tools 精确过滤与事件 3/18 的取舍

当前配置为 **thesis-sysmon-v1.1.1**。相对 v1.1.0，只新增一条 VMware Tools 注册表排除规则，继续保留事件 3、17、18、22。接收端、C# 采集器、预处理和命令参数没有变化；9 月 13 日的进度文件修复仍包含在完整包中。

## 能否通过 Sysmon 配置过滤

可以按字段值组合过滤整条事件。配置不是删除某几个输出字段，也不提供“同一个键每秒只记一次”的通用状态去重。时间窗口聚合、重复次数统计、字段归一化适合在原始日志之后进行。Sysmon 排除的事件不会进入通道，接收器无法再恢复它们。

不能只因为事件在正常系统中出现，就判定它没有分类价值。研究需要两类运行都包含一致的背景活动；从采集源排除，应优先针对已明确的实验工具行为，而不是按训练标签、样本路径、单轮 PID 或进程 GUID 排除。

## 事件 12：已加入的规则

新增规则放在现有 `RegistryEvent onmatch="exclude"` 中：

```xml
<Rule groupRelation="and">
  <Image condition="is">C:\Program Files\VMware\VMware Tools\vmtoolsd.exe</Image>
  <EventType condition="is">CreateKey</EventType>
  <TargetObject condition="is">HKLM\System\CurrentControlSet\Services\Tcpip\Parameters</TargetObject>
</Rule>
```

三个条件同时匹配才排除。使用固定安装路径和目标键的完整相等比较，避免一个宽泛排除条件覆盖其他进程或整个网络配置树。

以下事件仍按原有规则保留：

- vmtoolsd.exe 对该位置的值设置、删除和重命名。
- 对 `Parameters\NameServer`、`Parameters\Interfaces\...` 等值或子键的操作。
- reg.exe、样本进程或其他进程对该位置的建键操作。
- 其他路径下同名 vmtoolsd.exe 的活动，以及该程序其他位置的建键活动。

这不是按进程签名建立的可信身份判断；若同一安装路径的程序被替换或受到操纵，同样满足这三个字段的活动也会被过滤。这是此精确去噪规则的边界，不应把它扩展成对整个程序的放行。

没有按 UtcTime、ProcessId、ProcessGuid、User 设置固定条件；每轮时间和进程身份会变化。反复 CreateKey 也不能仅凭文本相同就认定是传输重复：需要比较原始 XML 的记录号和接收序号。

## 事件 18：保留，不能认定为我们的传输管道

你提供的是 `wmiprvse.exe → \srvsvc`。`srvsvc` 是 Windows Server Service Remote Protocol 使用的命名管道端点，可以包含服务管理/枚举的 RPC 上下文；仅凭这一条不能确认触发它的是正常管理工具还是样本活动。

本项目虚拟机 C# 程序打开的是 COM1，VMware 在物理机提供 `\\.\pipe\sysmon-log`，Python 连接这个端点。它与来宾中的 `\srvsvc` 不是同一个管道。此次不增加 `wmiprvse.exe`、`\srvsvc` 的全局排除，也不关闭事件 18。

技术上可以按 `PipeEvent` 的 `EventType=ConnectPipe` 排除所有连接事件而保留创建事件，但当前没有足够证据证明这个取舍适合主实验。若以后研究比较“不使用事件 18”的模型，应在保留原始数据的前提下生成派生视图，对两类样本一致地处理和比较结果。

## 事件 3：保留，先检查时间来源

示例是 `svchost.exe → 192.168.198.1:53/UDP`，与 DNS 请求流量相符。仅凭 IP 不能确认 `.1` 就是虚拟机网关，也不能据此推断与后端网站成功通信。Windows DNS Client 为应用提供名称解析，因此 svchost.exe 产生的此类流量不能直接判为与样本无关。

此次不排除这个 IP、不排除 UDP 53，也不整体排除 svchost.exe。事件 22 提供域名查询上下文，事件 3 提供网络端点上下文，两者不能简单互相替代。在离线实验中，即使查询失败，相关尝试仍可能有研究价值。

示例的 UtcTime 是 **2026-09-08 19:09:54.528**，而另外两条是 9 月 13 日。如果三条来自同一轮新采集，应优先比较事件 3 原始 XML 的 `System/TimeCreated/@SystemTime`、`EventData/UtcTime`、外层 `Record/@ReceivedUtc` 和本轮时间范围。目前不能只凭展示文本断定是旧记录还是时间源异常，也不能把该字段自动改成接收时间后当作真实行为时间。

健康关机快照冷启动后的试采仍需重新核验。这里没有修改网络、时间同步或快照，也不需要为了过滤问题给虚拟机开放网络。

## 部署

新版 XML SHA256：

```text
f296a1839987d26d824a8f3793e68329335368f95681135878ab6ff827438155
```

如果已部署 9 月 13 日版本，只需将新版 XML 复制到健康虚拟机对应位置，并更新配置。下面假设原来使用的 Sysmon 文件为 `C:\Sysmon\Sysmon64.exe`；名称或路径不同则替换为实际文件，无需更新 Sysmon 二进制。

```powershell
$config = 'C:\SysmonRealtime\sysmon\sysmonconfig-export.xml'
$expected = 'f296a1839987d26d824a8f3793e68329335368f95681135878ab6ff827438155'
if ((Get-FileHash -LiteralPath $config -Algorithm SHA256).Hash.ToLowerInvariant() -ne $expected) {
    throw 'Unexpected Sysmon config SHA256'
}
& 'C:\Sysmon\Sysmon64.exe' -c $config
if ($LASTEXITCODE -ne 0) { throw 'Sysmon config update failed' }
& 'C:\Sysmon\Sysmon64.exe' -c
```

配置更新只影响后续产生的事件。事件查看器里原来的事件 12 不会自动消失；不要把旧事件仍可见当作规则失效。更新健康快照，例如 `SysmonResearch_v1_1_1`，否则下次恢复旧快照会恢复旧规则。两类运行都使用同一新版配置，并按主 README 保存批次 XML 和配置哈希。

建议新批次目录：`D:\SysmonLogs\thesis-v1_1_1-batch01` 和 `D:\SysmonBenignLogs\thesis-v1_1_1-batch01`。完整采集命令仍见主 README。自动跳过逻辑不比较配置指纹，因此不要使用旧目录期待自动重采。

验证需要确认：实际加载配置中存在上述 AND 排除；新一轮中三条件匹配的记录不再出现；值修改、删除、子键及其他进程活动仍可见；核心 1/5/11/26、事件 3/18/22、窗口、最终计数及队列检查正常。仅看到 vmtoolsd 事件消失，并不能单独证明规则正确加载，它也可能没有在该轮触发。

本次在工作区更新配置与项目包，没有改写部署目录或历史 XML。7 项配置回归测试通过，包括精确匹配与相邻行为保留；与上版 XML 比较确认非注册表规则逐项不变、注册表仅新增上述一个 AND 规则。未在真实来宾 Sysmon 驱动中加载或进行吞吐测试。9 月 13 日的五轮规则回放报告仍对应 v1.1.0，不能拿其中比例声称本次 v1.1.1 的新实测效果。
